**Before every commit**, run `npm run format` to auto-fix formatting, then verify with `npm run format:check`. CI will reject unformatted code.

CI runs on every push/PR via GitHub Actions (`.github/workflows/ci.yml`): a `setup` job warms `node_modules`, then **10 parallel jobs**: `format-check`, `lint`, `typecheck`, `test` (with coverage + PR comment), `audit` (`npm audit --audit-level=high`), `dead-code` (knip), `test-integration` (spins up a Postgres 16 service), `test-e2e-browser` + `test-e2e-docker` (Playwright with required Docker images pre-pulled), and `build`. Tests are co-located next to source files (`*.test.ts`/`*.test.tsx`); integration and E2E live in separate top-level dirs and are excluded from the unit run via `vite.config.ts`. Node version is pinned in `.node-version` (currently 24) — CI reads it via `node-version-file` (the composite action `.github/actions/setup-node-and-deps` points at `.node-version`). Keep `.node-version`, `.nvmrc`, `package.json` engines, and your local Node version in sync to avoid lock file mismatches between local and CI. Prettier check is enforced in CI; before committing larger changes prefer `npm run format` over `:check` so the working tree is normalised.

## Local dev environment

- **Nix / direnv** (optional): `flake.nix` exposes a dev shell (Node 24, `prisma-engines`, `openssl`); `.envrc` runs `use flake` + `dotenv`. The shell hook exports `SANDBOX_RUN_AS_USER=false` because rootless setups can't map a host uid into sandbox containers.
- **Rootless Podman** is supported as a Docker drop-in: `scripts/podman.sh` proxies the rootless Podman socket to a Docker-compatible socket (`socat`) and runs `docker compose`. Under rootless Podman, set `SANDBOX_RUN_AS_USER=false` — `hardeningArgs()` in `code-container.service.ts` then drops the `--user=uid:gid` flag and the `uid=/gid=` tmpfs options (which Podman can't honour); sandbox tmpfs use `mode=0777` for the same reason.

## Architecture

CyberStars is a split-screen coding education platform (React frontend + Express backend + PostgreSQL).

### Client (`client/`)

- React 19 + Vite 7 + Tailwind CSS 4, uses HashRouter
- Routes: `/`, `/getstarted`, `/courses`, `/algorithms`, `/algorithms/:lang`, `/lesson/:category/:lesson`, `/profile`, `/settings`, `/u/:userId` (public profile), `/leaderboard`, `/messages`, `/connections`, `/forum`, `/almanac`, `/laniakea`, `/rules`, `/support`, `/welcome`, `/admin` (admin-only; client-side redirect is UX only — the API is server-authoritative)
- Three React Context providers: `AuthContext`, `CurriculumContext`, `ProgressContext`
- Services in `client/services/` wrap API calls through a shared `apiClient` fetch wrapper. Exceptions: `lessonService` and `almanacService` fetch **static files** (lesson markdown, `curriculum.json`, almanac JSON) directly via `fetch` — that content is generated into `public/` at build time and never hits the API server (see `scripts/generate-static-content.ts`)
- Code editor uses CodeMirror 4 with per-language syntax highlighting
- Global `CosmosBackground` (canvas starfield + nebulae) renders on all routes except `/getstarted` and `/welcome` — managed in `App.tsx` via `GlobalBackground` component. Uses `isolation: isolate` on `#root` with `z-index: -1` on cosmos so content stays above without explicit z-index hacks. AuthPage and WelcomePage have their own dedicated animated backgrounds.
- Text sections over the starfield use `.text-backdrop` class (semi-transparent bg + backdrop-blur) for readability

### Server (`server/`)

- Express 5 + TypeScript, runs with tsx
- `app.ts` exports the Express app (used by supertest); `server.ts` imports it and calls `listen()`
- Three-layer architecture: Routes → Controllers → Services → Repositories
- Zod schemas in `server/schemas/` validate all request bodies via `validateBody()` middleware
- Auth: JWT in httpOnly cookies, bcryptjs password hashing. The JWT payload carries only `{ id }` — the role is **never** in the token; any role/authorization check reads it fresh from the DB by the authenticated user id (`userRepo.getRole`), so a tampered client/cookie cannot escalate
- Admin: `requireAdmin` middleware (in `middleware/auth.ts`, runs after `authenticateToken`, DB-authoritative role check) gates `/api/admin/*`. `GET /api/admin/stats` returns platform aggregates (users/progress/forum/support) cached ~5min in `admin.service.ts` to spare the VPS, plus **live** in-memory code-execution metrics (`code-container.service.liveMetrics`) read on every call; `?fresh=1` force-bypasses the cache (used by the dashboard's Refresh button). No runs are persisted — code-exec stats are live-only
- Rate limiting: `express-rate-limit` on auth routes (10/15min) and terminal exec (30/min/user, with a friendly retry-after-Ns message via `execRateLimitHandler`). Editor code runs are rate-limited in the WebSocket layer (`ws-run.ts`): a fixed 10-runs/60s window per owner (same for guests and logged-in users) plus a 5-concurrent cap. Guests additionally get a **lifetime budget of 10 runs** (`guest-budget.service.ts`) before being nudged to sign up
- Code execution: Docker in all environments — language runtimes in `server/runtimes/` (c.ts, python.ts, java.ts, kotlin.ts). Required images: `gcc:latest`, `python:3.10-slim`, `eclipse-temurin:21-jdk-alpine`, `danysk/kotlin:latest`. Kotlin is a real `MAIN_COURSE_KEY` (seeded, runtime compiles to a jar with 512m memory) but its UI course card is badged "Coming Soon". Each **owner** (a logged-in user, or a guest keyed by a per-browser `guestId` cookie so shared-IP guests don't collide) gets **one long-lived container on their current language**, managed by `code-container.service.ts`: reused across runs (cold start paid once), **swapped on language change** (the previous language's container is torn down on the first run of the new one), hardened (`--network=none --cap-drop=ALL --security-opt=no-new-privileges --read-only`, non-root uid, tmpfs `/work` mounted **`exec`** so compiled C binaries can run, tmpfs `/tmp`), memory/pids capped. Idle containers are GC'd after 15min; a global LRU cap (`CODE_MAX_CONTAINERS`, default 50) bounds the total
- Interactive code execution via WebSocket at `/ws/run` — `interactive-execution.service.ts` writes the source into the owner's container (wiping `/work` first) and streams `docker exec` stdout/stderr via the `useCodeExecution` hook. 20s wall-clock timeout (resets on stdin), 1MB output cap; on timeout/cap/abandon the container is **destroyed** (reliably kills the program and children — killing the `docker exec` client alone wouldn't), on normal exit it's **kept for reuse**. A second `/ws/presence` connection (one per tab, opened by `usePresence` at the app root) lets the server tear down the owner's idle container promptly when the tab closes — ref-counted for multi-tab, with the 15min GC as backstop. `attachRunWebSocket` routes both paths through one manual `noServer` upgrade handler (two `{server, path}` servers corrupt each other's frames). In production, nginx must proxy `/ws/` (covers `/ws/run`, `/ws/presence`, and `/ws/user`) with `Upgrade` and `Connection "upgrade"` headers
- Shared per-user event socket at `/ws/user` (`ws-user.ts` registry `Map<userId, Set<WebSocket>>`, wired through the same `attachRunWebSocket` upgrade handler as the run/presence sockets). Requires a logged-in user and passes the `notifications` preview gate (same rule as the REST endpoints — 404 for non-admins on prod). Server-push only (no client messages); the server pushes `UserSocketFrame`s on two channels: `notification` (`new` / `unread-count`) and `dm` (`message` / `read` / `reaction`, used by messaging)
- **Notifications** (preview-gated, admins-only on prod): per-user in-app notifications for forum replies/accepted solutions/reactions, support ticket/reply/status events, and connection requests/acceptances (`CONNECTION_REQUEST`/`CONNECTION_ACCEPTED`). Emitted fire-and-forget via `notifications.service.notify()` (never throws), which **excludes the actor** from their own notification, dedupes recipients, collapses repeat `FORUM_REPLY`/`FORUM_REACTION` into one unread row (count++), and prunes each user to a 100-row retention cap. There is **no** DM notification type — the messages badge already covers new messages (`DM_MESSAGE` was removed from the enum with a data migration). Actor name/avatar come from the `actor` DB relation (single source of truth, `SetNull` on delete), NOT snapshotted; only the source-entity title/excerpt/etc. is snapshotted into `data`. REST: `GET /api/notifications`, `POST /api/notifications/read` (up-to-id), `POST /api/notifications/:id/read`. Client: `NotificationContext` + `useUserSocket` drive a bell + dropdown in the Topbar
- **Messaging (DMs)** (preview-gated `messaging`, admins-only on prod; no guests): 1-on-1 conversations at `/messages` via `/api/messages` REST — inbox with unread counts, open conversation, paginated history, send, mark-read up-to-id, soft-delete own message, and toggle emoji reaction (per-user rate limits on open/send/react; reactions 60/min). Models `Conversation`/`DirectMessage`/`DmReaction` (reactions unique per message+user+emoji; the server returns raw per-user rows and the client groups by emoji). Live updates ride the `/ws/user` socket's `dm` channel: `message`, `read`, and `reaction` frames (a toggle pushes the message's full refreshed reaction list to both participants). Client: `MessagesContext`; usernames in the forum and the DM thread header link to public profiles via the shared `UserLink` component (gated like public profiles)
- **Connections** (preview-gated `connections`, admins-only on prod; no guests): person-to-person connection requests — a directed `Connection` row (requester → addressee, status `PENDING`/`ACCEPTED`) that becomes mutual once accepted. `@@unique([requesterId, addresseeId])` blocks a duplicate in the same direction; the service checks the reverse so A→B and B→A can't coexist. REST under `/api/connections`: `GET /` overview (accepted + incoming + outgoing pending), `POST /` send (30/min/user — the only endpoint that reaches arbitrary user ids), `POST /:id/accept` and `/:id/decline` (addressee-only), `DELETE /:id` (cancels the caller's own pending request or removes an established connection). The recipient gets a `CONNECTION_REQUEST` bell, the requester a `CONNECTION_ACCEPTED` on acceptance; responding auto-reads the request's bell entry via `markEntityRead`. Client: `/connections` page + Topbar `ConnectionsButton`; public profiles render a connect/pending/connected button from `connectionRelation`
- Password reset: `/auth/forgot-password` sends a 6-digit code via email (15min expiry), `/auth/reset-password` validates code and updates password
- Terminal (Linux course): sandboxed Docker containers (`cyberstars-linux-sandbox`), stateful sessions with in-memory Map, idle GC at 15min. Container flags: `--network=none --memory=128m --pids-limit=64 --cap-drop=ALL --security-opt=no-new-privileges --read-only` plus tmpfs mounts for `/home/student` and `/tmp` (`mode=0777` for Podman compatibility). **Works for guests as well as logged-in users**: routes use `optionalAuth` and key sessions by `userId ?? guestId` cookie — the same owner model as editor code runs (running needs no account; only saving progress does)

### Database (`prisma/`)

- PostgreSQL via Prisma 6 ORM
- Core models: `User`, `Curriculum` (with `CurriculumKind` enum: editor/terminal), `Lesson`, `UserLessonProgress`, `UserSavedCode`, `DailyPick` (today's featured lesson/algo pick per user, see Daily picks below)
- Forum models: `ForumCategory`, `ForumThread`, `ForumPost` (soft-delete with `deleted`/`deletedByName`, edit tracking with `editedByName`), `ForumReaction`, `ForumThreadView` (unique view tracking — one row per `threadId` + `viewerKey` where `viewerKey` is `user:<id>` or `guest:<guestId>`; the thread's `views` counter increments only on the first view per viewer)
- Support models: `SupportTicket`, `SupportMessage` — tickets are per-user with threaded replies; owners can close their own tickets, admins can set any status
- Social models: `Conversation`, `DirectMessage` (soft-delete), `DmReaction`, `Connection` (directed request, `ConnectionStatus` enum), `Notification`
- Seed script populates courses and lessons from `prisma/curriculum.data.ts` (the single source of truth for curriculum structure, shared with the static-content generator)

### Shared (`shared/`)

- DTO types and constants imported by both client and server — keeps request/response shapes and course key constants in sync. Badges are derived client-side only (`useGamification`) from completion counts. XP formulas (`xpForLesson`/`xpForCourse`/`levelFromXp`/`xpForLevel`/`levelTitleKey`) live in `shared/constants.ts` so client and server compute identical values

### Lesson content (`server/lessons/{python,c,java,kotlin,linux}/`)

- Markdown files with fenced code blocks (` ```python `, ` ```c `, ` ```java `, ` ```kotlin `, ` ```bash `) for runnable examples and ` ```text ` for output
- Every C code block must include `#include`, `int main(void)`, `return 0` (full compilable program)
- Every Java code block must include `public class Main` with `public static void main(String[] args)` wrapper
- Intentional compile errors (e.g., demonstrating `if(x=2)` bug) still have full boilerplate — the error is only on the line being demonstrated
- Linux lessons: each slug has 2 files — `<slug>.md` (no H1, space-station theme) and `<slug>-setup.json` (sandbox filesystem). 55 lessons. Shared types in `shared/terminal.ts`. All 55 also ship a `<slug>-tests.json` (state-check **terminal judge**, see below), so the Linux course is judge-completable
- **Terminal judge** (`terminal-tests.service.ts`, endpoint `POST /api/terminal/check`, 10/min/owner): a DIFFERENT model from the code judge. It validates sandbox **state** against the student's live session container via one batched `docker exec bash -c` running assertion probes (`file_exists`/`dir_exists`/`path_exists`/`path_absent`/`files_equal`/`dirs_equal`/`file_contains`/`file_mode`/`command_output`), PLUS command-trace `requires`/`forbids` (`kind: command` with `name` word-boundary match or raw `pattern`) matched against `session.history` **server-side**. `cwd_is` is also evaluated server-side (no container call). `command_output` ships the produced stdout back base64-encoded and compares on the server via `compareOutputs(expected, actual, 'trimmed')` — but because that comparator re-runs the reference and doesn't trim _leading_ whitespace, prefer `requires` pattern gates for fragile output (uniq -c, recap text). Spec loads via `loadTerminalTestsSpec(course, slug, lang)` which prefers `ro/<slug>-tests.json` when `lang=ro` and it exists, else falls back to EN — RO lessons whose setup filenames are translated need a paired RO tests file using the Romanian paths. Completion is server-authoritative like the code judge (`markComplete` only on a passed verdict for a logged-in user; guests can run but not save). `hasTests` for Linux is generated into `curriculum.json` from EN tests-file existence
- **Optional solution files**: a lesson may ship a `<slug>-solution.md` (a single fenced runnable block solving the lesson's Mission). When the file exists, `LessonPage` shows a "Show Solution" button (in the lesson toolbar's "⋯" menu) that opens `SolutionModal` (markdown → runnable `CodeCell`); no file means no button. Loaded via `lessonService.fetchLessonSolution`, localized like any other lesson file (`ro/` subfolder, English fallback). Linux lessons follow the same file/button/modal mechanism, but the fenced block (` ```bash `) isn't wired into `CodeCell` (bash isn't an `EDITABLE_LANGS` entry), so it renders as a static command + expected-`` ```text` `` output transcript rather than something runnable — the button lives in `TerminalPanel`'s header instead of the editor toolbar
- **Optional judge tests**: a main-course lesson may ship `<slug>-tests.json` next to its markdown (currently the first 60 Python lessons, all 49 Java lessons, and all 47 C main-course lessons — including the OS block 39–47, which are graded via the oracle + `stdin` model with no injection). The judge (`lesson-tests.service.ts` dispatches per language: trusted `lesson-tests.runner.py` for Python, `lesson-tests.runner.java` for Java — both executed in the owner's warm Docker container; C is different — structure checks and value injection run **server-side** via `web-tree-sitter` (WASM) in `c-analysis.ts` (`prepareC`), and the container runner `lesson-tests.runner.c.py` is thin (compile + run only). C uses **injection** — splicing `init_declarator` initializer byte-ranges for initializer lessons — and **per-case `stdin`** for scanf lessons; C structure `kind`s are `call`/`variable`/`function`/`loop`/`int_literal`/`comment`/`string_expr`, no `fstring`) runs the student's code AND the reference `<slug>-solution.md` per case, **injecting** each case's values into both programs (Python via `ast`, Java via the javac Compiler Tree API — fixed variable names, the mission names the contract, with free values; a whole list is injected via `{ "$list": [...] }`, a whole dict via `{ "$dict": {...} }` with order preserved, and `$list`/`$dict` nest for lists-of-tuples etc.) and/or **feeding a per-case `stdin`** to both, then compares outputs **on the server** (expected output never enters the container). Java injection splices the initializer of a variable declaration (field or method-body local), so OOP lessons bind values into named locals before `new X(...)` rather than passing literals directly to constructors; the mission names those variables. Structure rules per lesson: `requires`/`forbids` with kinds `call`, `variable`, `function`, `loop`, `fstring`, `int_literal`, `comment` (require-only; `contains` substring matched whitespace-insensitively against real comments — py `tokenize`, java lexical scan, c tree-sitter `comment` nodes), and `string_expr` (forbid-only; catches the "wrap the line in quotes" fake-comment cheat — py/c only, N/A in Java where an unknown kind fires as a forbid). Comment lessons pair `comment contains <expr>` with `forbids string_expr` so quoting-out or deleting the target line fails. **Locale pairing invariant**: `ro/<slug>-tests.json` + `ro/<slug>-solution.md` are a unit (RO lessons use Romanian identifiers); if a lesson has a RO solution it MUST get a RO tests file, or injection silently no-ops and hardcoding passes. `hasTests` is generated into `curriculum.json` from the EN tests-file existence. UI: tested lessons show a Run Tests button; untested main-course lessons show the button disabled with a "Coming soon"/"Urmează" tooltip. There is **no manual "mark complete"** — completion comes only from passing the judge, and is **server-authoritative**: `tests.controller.runTests` calls `progressService.markComplete` itself on a `passed` verdict for a logged-in user (guests have no progress), so completion cannot be spoofed by a direct API call. The client just refreshes progress afterward. Endpoint `POST /api/tests/:courseKey/:lessonSlug/run` (10 runs/min/owner, works for guests). Full as-implemented spec + authoring checklist: §0 of `TESTS-DESIGN.md` at repo root (gitignored, local working doc)
- **Translations**: English is the source of truth and lives at the top level. Optional Romanian translations sit in a `ro/` subfolder beside the English source (`server/lessons/<course>/ro/<slug>.md`, reusing the same slug); `lessonService.getLocalizedText` requests the `ro/` path and falls back to English when it's missing, so a course can be translated one lesson at a time and English-only lessons work in both languages. The almanac follows the same pattern under `public/almanac/ro/` (`almanacService`). Linux `-setup.json` sandbox files can be localized too: an optional `server/lessons/linux/ro/<slug>-setup.json` (translated filenames + content) is picked up when the client's active language is `ro` — `useTerminalSession` passes `lang` on session create, `terminal-session.service.loadSetup` falls back to the English copy when no RO variant exists, and switching language mid-lesson tears down and recreates the sandbox. Romanian lesson **code and output must stay ASCII** — no diacritics inside ` ```py `/` ```text ` fences or `-code.md` files (printed strings, expected output, comments); diacritics belong only in the RO prose/theory

### Algorithm challenges (`server/algorithms/{python,java,c}/`)

- Separate from main lessons — mapped via `server/services/paths.ts`: course keys `algo-python`, `algo-java`, `algo-c` resolve to `server/algorithms/{python,java,c}/`
- Each challenge has 3 files: `<slug>.md` (problem statement with Input/Output/Examples), `<slug>-code.md` (starter code), and `<slug>-solution.md` (single fenced runnable block, powers the same "Show Solution" button/`SolutionModal` as lesson solutions)
- 20 challenges each for Python and Java; C has 32 (20 core + 12 concurrency-focused: fork/pipe/threads/mutex/semaphore) — Easy/Medium/Hard, registered in `prisma/seed.ts`
- Starter code (`<slug>-code.md`) is empty — Python is 0 bytes, Java/C are 3 blank lines (no compilable wrapper); students write the full solution, including the `class Main`/`#include`+`int main()` boilerplate for Java/C, from scratch
- Solutions are provided for all 72 challenges (Python 20, Java 20, C 32), EN + RO
- Algorithm challenges are **judge-graded** (the same server-authoritative judge as main-course lessons — see Lesson content): all 20 algo-python + all 20 algo-java + all 32 algo-c challenges ship a `<slug>-tests.json`. The 12 algo-c concurrency challenges (fork/pipe/threads/sem) are now graded too via the nondeterminism-tolerant comparators below. Algo challenges read stdin, so tests use the oracle + per-case `stdin` model (no injection); a single EN tests file suffices unless the RO solution's output diverges (translated words, or Romanian command keywords in stdin), which gets a paired `ro/<slug>-tests.json`. matrix-multiply (java) / matrix-transpose (c) have fixed input, so they use a `structure.requires: loop` check. Because algo is now completable, XP display is **enabled** on algo pages (LessonPage header + completion toast). `hasTests` distinguishes graded from ungraded challenges (Run Tests button state)
- **Output comparators** (`compareOutputs` in `lesson-tests.service.ts`, `TestComparator` in `shared/tests.ts`): `trimmed` (default — trims trailing whitespace + trailing blank lines), `exact` (byte equality), `masked` (collapses every `\d+` run to `#` — for fork/getpid lessons that print nondeterministic **PIDs** in a fixed line order), `unordered` (compares the **multiset of lines** — for thread/process lessons whose line **order** varies between runs, e.g. fork-workers, os-threads, os-semaphores). `masked`/`unordered` lessons pair a minimal `structure.requires` on the libc primitive (`fork`/`pthread_create`/`sem_wait`/`pipe`) — libc names the student can't rename, so freestyle on identifiers stays intact while hardcoding the fixed output is blocked. Fixed-input deterministic lessons (os-pipes, os-semaphores-signal, recap-os) rely on the same structural gate since varied stdin can't protect them

### Testing (`test/`)

- Vitest with jsdom environment, `@testing-library/react` + `@testing-library/jest-dom`
- Setup file in `test/setup.ts` handles jest-dom matchers and cleanup between tests
- Coverage via `@vitest/coverage-v8` with json-summary + lcov reporters
- Client component tests use `render`/`screen`/`fireEvent` from testing-library
- Server unit tests on services use `vi.mock` to isolate from env/DB dependencies (see `progress.service.test.ts`)
- Endpoint smoke tests (`server/app.test.ts`) use supertest to verify all routes respond correctly (200 for public, 401 for auth-protected, 404 for unknown). Mock PrismaClient and repositories to avoid needing a real DB
- Dead code detection via knip (`npm run dead-code`) — config in `knip.config.ts`. Runs in CI; must pass before merge
- Coverage thresholds enforced in `vite.config.ts`: **90% on all metrics** (lines/statements/functions/branches) — `npm run test:coverage` fails if below
- Code formatting via Prettier — config in `.prettierrc`, check with `npm run format:check`, fix with `npm run format`
- **Integration tests** (`test/integration/`) run against a real PostgreSQL DB (config in `vitest.integration.config.ts`). `global-setup.ts` runs `prisma migrate deploy` + seed once; per-file `setup.ts` truncates app tables before each test and inserts a Sentinel ADMIN so `createAuthenticatedAgent()` returns regular USERs (first-registered-user auto-promotes to ADMIN). Tests are serial (`fileParallelism: false`) to avoid DB contention. Requires `.env.test`
- **E2E tests** (`e2e/`) use Playwright with two projects: `browser` (auth/forum/support/courses/profile via `npm run dev` webserver) and `docker` (code execution paths — needs all runner Docker images plus `cyberstars-linux-sandbox` built locally). `e2e/global-setup.ts` migrates+seeds; `e2e/fixtures/test.ts` provides an `authedPage` fixture that resets the DB and signs up a fresh user via the API before each test. The webserver autostarts the dev stack when no server is running on :5173
- CodeMirror auto-pairs `{`, `(`, `[`, `"`. In E2E tests, multi-line code typed with `keyboard.type` may produce duplicate `}` — keep test code on a single line so the typed `}` skips over the auto-paired one

- DigitalOcean VPS, app at `/opt/cyberstars`, managed by pm2 (`pm2 restart cyberstars`)

## Key conventions

- Vite proxies `/api`, `/auth`, and `/ws` to the Express server (configured in `vite.config.ts`)
- Course metadata is centralised in `client/constants/courses.ts` via `courseMeta(key)` and `courseTitle(key)` — single source of truth for icons, colors, labels
- Course key constants live in `shared/constants.ts`: `MAIN_COURSE_KEYS`, `ALGO_COURSE_KEYS`, `TERMINAL_COURSE_KEYS`, `ALL_COURSE_KEYS`
- Gamification is derived client-side from `UserLessonProgress` counts — no separate gamification tables. **Badges**: "First Steps" (1 lesson) and Bronze/Silver/Gold tiers (10/20/30 lessons per course); new earnings trigger a 5s toast. **XP & levels**: XP is a _derived_ quantity, never stored nor accepted from a client — the server recomputes `earnedXp`/`totalXp` in `getCourseProgress` from the sortOrder of judge-completed lessons (`xpForLesson(sortOrder) = 10 + (sortOrder - 1)` — sortOrder is **1-based** per `prisma/curriculum.data.ts`, so the first lesson is worth 10 XP), so a tampered client can only fool its own display (completion rows are server-authoritative). Completion rows created by the old manual mark-complete flow are **grandfathered**: they stay in the DB and still yield XP (deliberate decision — no destructive migration; anti-cheat is forward-looking only). Quadratic level curve `levelFromXp(xp) = floor(sqrt(xp/100)) + 1` with cosmos-themed titles (`level.title.1..10` i18n keys); `useGamification` aggregates XP across courses. Shown in Profile (level banner + progress bar), Topbar (level chip), and the lesson-completion toast (`+N XP`). An XP-ranked leaderboard (`/api/leaderboard`) is launched to logged-in users only — the `leaderboard` feature is no longer preview-gated, but the route adds `authenticateToken` so guests are kept out (the page exposes `total`, the platform-wide account count)
- **Daily picks** (`/api/daily`, auth-required; `daily.service.ts` + `daily.repository.ts`): `GET /api/daily` returns today's `lesson` and `algo` picks plus `bonusRatio`. Each pick is chosen **deterministically per day+kind** from a course pool (`lesson` = main + terminal courses, `algo` = algo courses) via a stable hash seed, so every user sees the **same** pick that day; the concrete row is then persisted **per user** (`DailyPick`, unique `[userId, date, kind]`) only so the bonus can be tracked. Only judge-completable lessons are eligible (an ungraded pick would be unclaimable). Completing today's pick **on its day** grants a one-time bonus of `DAILY_BONUS_RATIO` (0.2 = **+20%**) of the lesson's base XP: `progressService.markComplete` calls `dailyService.awardBonusForCompletion` (idempotent, sets `bonusAwarded`), and `getCourseProgress` folds awarded bonuses back into `earnedXp` via `dailyRepo.getAwardedSlugs`. Surfaced on the home page and the `/laniakea` explorer (`LaniakeaExplorerPage`)
- Profile features (avatar upload, bio, status with 24h expiry) via `/api/profile` routes with multer + magic-byte validation. Uploads served from `/uploads` static dir. Profile editing plus the language/background/privacy toggles live on a dedicated `/settings` page (moved out of the Topbar dropdown). Five per-user privacy flags on `User` (`showBio`/`showStats`/`showProgress`/`showActivity`/`showConnections`, default on) are set through the same `PATCH /api/profile` and gate the public profile's sections
- Public profiles at `/u/:userId` (reached from the leaderboard rows) via `GET /api/users/:id/profile` → `public-profile.service.ts`, gated with the same `leaderboard` feature key and logged-in only (the route uses `authenticateToken`, so guests get 401 — no guest can view a profile or the forum username links that share this gate). Name/avatar/member-since are always public to any logged-in viewer; bio/status, stats (lessons done, active courses, streak), progress (level, XP, rank, badges), the activity heatmap, and the connections list (truncated for display but with the true total `count`) each appear only when the target's matching privacy flag is on — the owner viewing their own profile (`isSelf`) always sees everything. The payload also carries `connectionRelation` (`self`/`none`/`pending_outgoing`/`pending_incoming`/`connected`) for the profile's connect button. Streak logic is shared via `activity.service.computeStreak` (used by both this and `GET /api/profile/activity`)
- Dark theme uses CSS custom properties with accent purple `#6C5CE7`, Space Grotesk font for UI, JetBrains Mono for code
- Lesson completion is driven **only** by passing the judge and is **server-authoritative**: `tests.controller.runTests` calls `progressService.markComplete` when the judge returns `passed` for a logged-in user. There is no client-writable completion endpoint (`POST/DELETE /api/progress/:courseKey/:lessonSlug/complete` were removed), so completion cannot be spoofed. The client reflects it optimistically then `refresh()`es. There is no manual "mark complete" button anywhere — Python, Java, and C main-course lessons (including the C OS block 39–47), all 55 Linux/terminal lessons (via the terminal judge), plus the graded algorithm challenges (all algo-python/algo-java, all 32 algo-c including the 12 concurrency ones) are judge-completable; only Kotlin (course "Coming Soon") lacks tests and is not completable yet
- The user communicates in Romanian; code and docs stay in English
- **No ALL-CAPS anywhere** unless the user explicitly asks for it — this covers UI copy, i18n strings, lesson content/output, comments, and CSS uppercase transforms (`uppercase`, `text-transform`). Prefer normal sentence case for new labels and section headers
- i18n: bilingual UI (English default + Romanian) via i18next; toggle persists to `localStorage` (`cyberstars.lang`). UI strings in `client/i18n/locales/{en,ro}.json` (keep keys in sync). Lesson/almanac content is translated by file in `/ro` subfolders with English fallback (see Lesson content). `SUPPORTED_LANGS = ['en', 'ro']` in `client/i18n/index.ts`
- Page wrapper divs use `bg-transparent` (not `bg-[var(--bg)]`) so the global cosmos starfield shows through
- All cards, panels, and containers use very low opacity backgrounds (`rgba(22,22,29,0.1)` with `backdrop-blur-[12px]`) so the cosmos is visible through them. Never use opaque backgrounds (`bg-[var(--bg2)]`, `bg-[var(--surface)]`) for content panels. The canonical single-source utility is the **`.panel`** class in `index.css` (this exact glass surface + accent/30 border + `rounded-xl`) — prefer adding `panel` over re-inlining the background/blur/border. The `.text-backdrop` header class shares the same glass surface (just with built-in padding), so page headers and content panels read as one consistent background
- Panel/card borders use accent purple at 30% (`border-[var(--accent)]/30`), not `border-[var(--border)]`
- Internal separators (`border-b`, `border-t`) use `border-[var(--accent)]/20`
- CodeMirror editor has transparent backgrounds via global CSS overrides (`!important`) in `index.css` — `.cm-editor`, `.cm-line`, `.cm-content`, `.cm-gutters` are all transparent
- Topbar is semi-transparent (`rgba(22,22,29,0.78)` + `backdrop-blur`) — not opaque
- ESLint uses `typescript-eslint` parser with separate configs for `.ts/.tsx` (browser globals) and `.js` (node globals). Unused args prefixed with `_` are allowed via `argsIgnorePattern`
