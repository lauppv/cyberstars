## Commands

```bash
npm run dev               # Start client (Vite :5173) + server (:5000) + db setup concurrently
npm run dev:client        # Vite dev server only
npm run dev:server        # Express server with tsx watch
npm run build             # Production build to apps/ui/dist (gen:content first via prebuild, then pre-renders the landing page into index.html)
npm run gen:content       # Generate apps/ui/public/curriculum.json + lessons/ static files (auto-run by predev:client & prebuild)
npm test                  # Run Vitest unit suite once (UI on jsdom, API on Node)
npm run test:watch        # Vitest in watch mode
npm run test:coverage     # Vitest + v8 coverage (./coverage/); fails if below thresholds
npm run test:integration  # Real-Postgres integration tests (apps/api/test/integration/, requires .env.test)
npm run test:e2e          # Playwright (both projects: browser + docker)
npm run test:e2e:browser  # Playwright browser-only (auth/forum/support/courses/profile)
npm run test:e2e:docker   # Playwright docker runners (Python/C/Java/Kotlin/terminal/ws-stdin)
npm run test:e2e:ui       # Playwright UI mode
npm run typecheck         # tsc on the UI, the server (+ scripts, integration tests, Prisma) and E2E
npm run lint              # ESLint
npm run format            # Prettier write
npm run format:check      # Prettier check (CI-equivalent)
npm run dead-code         # knip: find unused files, exports, and dependencies
npm run db:prepare        # Prisma generate + migrate + seed
npm run db:migrate        # Run pending migrations (prompts for name)
npm run db:deploy         # Apply migrations without prompts (CI/prod)
npm run db:seed           # Seed curriculum and lessons into PostgreSQL
npm run db:studio         # Open Prisma Studio GUI
npx vitest run path       # Run a single test file (substring match)
npm run check:tutor       # Push the real tutor with apps/api/scripts/tutor-redteam.json, grade its code with the judge (Gemini key + Docker)
```

**Before every commit**, run `npm run format` to auto-fix formatting, then verify with `npm run format:check`. CI will reject unformatted code.

CI runs on every push/PR via GitHub Actions (`.github/workflows/ci.yml`): a `setup` job warms `node_modules`, then **11 parallel jobs**: `format-check`, `lint`, `typecheck`, `test` (with coverage + PR comment), `audit` (`npm audit --audit-level=high`), `dead-code` (knip), `validate-tests` (`npm run validate:tests`), `test-integration` (spins up a Postgres 16 service), `test-e2e-browser` + `test-e2e-docker` (Playwright with required Docker images pre-pulled), and `build`. A second workflow, `.github/workflows/lesson-tests.yml`, grades lessons again through the real judge (`check:tests`) on PRs, but only the ones the PR can have changed: `apps/api/scripts/changed-lessons.ts` maps a changed spec, solution or variant to that lesson (EN + RO), a runner to every lesson of its language (EN only, sharded: Python 2, C 1, Java 4), and the judge engine shared by all three to every language; a PR touching none of them skips it, one touching only the planner or the workflow grades one lesson per language, and a manual run (`workflow_dispatch`) grades every lesson in EN and RO. Tests are co-located next to source files (`*.test.ts`/`*.test.tsx`); integration tests live in `apps/api/test/integration/` and E2E in `e2e/`, outside the unit projects in `vitest.config.ts`. Node version is pinned in `.node-version` (currently 24); CI reads it via `node-version-file` (the composite action `.github/actions/setup-node-and-deps` points at `.node-version`). Keep `.node-version`, `.nvmrc`, `package.json` engines, and your local Node version in sync to avoid lock file mismatches between local and CI. Prettier check is enforced in CI; before committing larger changes prefer `npm run format` over `:check` so the working tree is normalised.

## Local dev environment

- **Nix / direnv** (optional): `flake.nix` exposes a dev shell (Node 24, `prisma-engines`, `openssl`); `.envrc` runs `use flake` + `dotenv`. The shell hook exports `SANDBOX_RUN_AS_USER=false` because rootless setups can't map a host uid into sandbox containers.
- **Rootless Podman** is supported as a Docker drop-in: `scripts/podman.sh` proxies the rootless Podman socket to a Docker-compatible socket (`socat`) and runs `docker compose`. Under rootless Podman, set `SANDBOX_RUN_AS_USER=false`. `hardeningArgs()` in `code-container.service.ts` then drops the `--user=uid:gid` flag and the `uid=/gid=` tmpfs options (which Podman can't honour); sandbox tmpfs use `mode=0777` for the same reason.

## Architecture

CyberStars is a split-screen coding education platform (React frontend + Express backend + PostgreSQL).

### Client (`apps/ui/`)

- React 19 + Vite 7 + Tailwind CSS 4, uses BrowserRouter: real addresses, no `#`. Romanian pages live under `/ro`, set in `App.tsx` as the router's `basename` from the address the app loaded on, so every route, link and `pathname` check is written once and works in both languages. The `@cyberstars/ui` workspace: code in `apps/ui/src`, page shell, static files and Vite config next to it, its own `package.json`. Vite reads the root `.env` (`envDir`) and builds to `apps/ui/dist`, which the server serves
- Routes: `/`, `/getstarted`, `/courses`, `/courses/:course` (a course's syllabus; `/courses?open=<key>` is the old way to say it and redirects), `/algorithms`, `/algorithms/:lang`, `/lesson/:category/:lesson`, `/profile`, `/settings`, `/u/:userId` (public profile), `/leaderboard`, `/messages`, `/connections`, `/forum`, `/almanac`, `/almanac/:slug` (an open article), `/laniakea`, `/rules`, `/support`, `/welcome`, `/admin` (admin-only; client-side redirect is UX only, the API is server-authoritative), and `*`, a not-found page. Every route must be either one of the public pages the build pre-renders or listed in `APP_ONLY_PATHS` (`packages/shared/routes.ts`); `App.routes.test.ts` checks it, since the server answers 404 for anything else
- Three React Context providers: `AuthContext`, `CurriculumContext`, `ProgressContext`
- Services in `apps/ui/src/services/` wrap API calls through a shared `apiClient` fetch wrapper. Exceptions: `lessonService` and `almanacService` fetch **static files** (lesson markdown, `curriculum.json`, almanac JSON) directly via `fetch`. That content is generated into `apps/ui/public/` at build time and never hits the API server (see `packages/content/scripts/generate-static-content.ts`, which the UI's `gen:content` runs with its `public/` folder)
- Code editor uses CodeMirror 6 (`@codemirror/*` 6.x, wrapped by `@uiw/react-codemirror` 4.x) with per-language syntax highlighting
- **App shell** (`apps/ui/src/components/layout/AppShell.tsx` + `Sidebar.tsx`): every route except `/getstarted`, `/welcome`, `/laniakea` and a visitor's welcome page on `/` (also bare while sign-in is still loading, so it never flashes) renders inside a Linear-style left sidebar (240px, lucide-react icons). Main nav (Dashboard/Courses/Algorithms/Almanac), a Community group (Forum/Messages/Connections/Leaderboard, then a line and Tutor; gated preview features stay listed with a "Coming soon" tag but lead nowhere), Support/Settings and an account menu (profile, usage, rules, admin, sign out) at the foot. Above 768px the sidebar pushes the page aside; below it slides over as a drawer with a backdrop, closes on navigation/Escape, and always starts closed on a phone. The open/closed choice persists in `localStorage` (`cyberstars.sidebar`). `useSidebar()` exposes `{ state, toggle }` (null outside the shell); the Topbar's panel button uses it. `/laniakea` and `/welcome` (the old welcome tour, replaced by the landing page) are still routed but deliberately have no link anywhere in the UI
- **Tutor panel** (`apps/ui/src/components/tutor/` + `context/TutorContext.tsx`, CYB-15): the sidebar's Tutor entry, a button after Leaderboard and a line, behind the `tutorChat` gate, opens a new general conversation in a panel on the right, the window's full height, or closes the panel when it shows a general one. `TutorProvider` sits above `AppShell`, so the conversation, and an answer still arriving, carries on across pages; it forgets them when the account changes. It keeps every conversation it has opened, saved or new, under a key of its own, with its own messages, answer in progress and error, and shows one. A new conversation has no id until the `done` (or `error`) event of its first answer names the one the server saved it to, and every later message sends that `conversationId`; an untouched new one is shown again rather than another started. "Ask the tutor", first in the code editor's ⋯ menu on a lesson or algorithm challenge (CYB-17) and in `TerminalPanel`'s ⋯ menu on a Linux lesson (CYB-67), calls `openLesson(lesson)`: the lesson's conversation the panel showed last, else its newest saved one from the history, else a new one about it. The header's pen starts a new conversation about what the shown one is about. **History** (`TutorHistory`): the header's panel button opens a 240px column to the left of the panel that pushes the page aside like the panel does (on a phone it covers the panel and closes once a conversation is picked), remembered in `localStorage` (`cyberstars.tutorHistory`). It lists `GET /api/tutor/conversations` under Today, Yesterday and Earlier, each by its title with its lesson's title from the curriculum or "General", read when the panel first opens and again after every saved answer; a lesson's conversation opens on its lesson's page (`navigate`), so the tutor sees the work there. `LessonPage` keeps the work in a ref (the code, the last `TUTOR_RUN_OUTPUT_MAX_LENGTH` characters of the run's output, and the `submission.id` of the verdict on screen; on a Linux lesson no code, the last `TUTOR_RUN_OUTPUT_MAX_LENGTH` characters of the terminal session with each command after `$ `, and the checks of the last Run Tests in the words the student reads) that `send` reads when a message goes, registered with `enterLesson` from an effect while the page is open. The function it gets back runs from the effect's cleanup and closes the panel if it shows that lesson, but only once a microtask finds the lesson still gone, so StrictMode's second mount or a fresh render of the same lesson doesn't close it. An answer still arriving when the student switches or leaves carries on in its own conversation. In a lesson chat an in-app link in an answer shows as plain words (`TutorAnswer`'s `onInAppLink` is null). `AppShell` renders `TutorPanel` while it is open and pushes the page aside for its 400px, and 640px with the history (`tutorRoom`), whenever that leaves the page about 360px: from 768px with the sidebar closed (640px from 1024), from 1024px with it open (640px from 1280). Narrower than that they lie over the page, and below 768px the panel covers the screen. The page wrapper is a size container (`@container`), so `LessonPage` splits text and editor from `@2xl` (672px of room) and narrows its band to 4/5 from `@5xl`, and the course, algorithm, home, admin and message grids switch columns on the room left too, not on the window. `tutorService.streamChat` reads the SSE body with a stream reader and hands each `TutorStreamEvent` over; until the first words `TutorStatus` says what the tutor is doing under a purple `.animate-glimmer` (still under reduced motion): the last `status` lookup the server sent (searching the lessons, reading one by its title, going through the app's pages), else looking at the work in a lesson chat and thinking in a general one. An answer cut by the length limit gets a note, one blocked before any words a short line instead of a bubble, and one blocked after some words its words with a note (`tutor.blockedMidway`), live and saved. A failure before any words, a plain error response or an `error` event with no words before it, shows the question again with a localized error and Try again; after some words the partial answer stays (the server saved it as `interrupted`) with Try again. Answers are markdown through `TutorAnswer`: an in-app link is a router `Link` (on a phone it also closes the panel), others open in a new tab, a code block that names Python, Java or C is coloured in the editor's oneDark by `TutorCode` (loaded lazily, with the editor's own lezer parsers; the colours are the `.tok-*` rules in `index.css`) and any other stays plain `pre`, images are dropped. Everything the tutor says sits beside `TutorMark` (the sidebar's `TutorFace` on an accent tint, also in the header), and the student's bubbles are an accent tint. `TutorFace` (`components/tutor/TutorFace.ts`) is the brand star round enough to hold a face, made with lucide's `createLucideIcon` so it stands wherever a lucide icon does (the sidebar, the ⋯ menus); it has a thinking and a happy twin. `TutorMark` takes a `mood`: the header's and the answer's think until its first words, and both the header's and an empty conversation's smile while there is a cheer; the header's and the empty conversation's blink every 5 s while idle (`.tutor-blink` on the idle face's `.tutor-eyes`, off under reduced motion), the small one beside each answer keeps still. An empty conversation shows the mark, a title (a greeting by the student's first name and the hour: morning from 5, day from 12, evening from 18, late from 23; "How can I help?" without a name), the intro and three questions to start with that send on a click. A general conversation gets three of `GENERAL_STARTERS` (14) at random each time `showNew` makes it, the first one fitting the page on `/algorithms` and `/courses` (`PAGE_STARTERS`); picked in the handler, not while rendering. A lesson chat's follow where the student stands (`lessonStarters`): `LessonPage` tells `reportStage(lesson, stage)` from an effect, `empty` (no code beyond the starter, or no command typed), `working`, `failing` (with the test it stopped on, numbered from 1, when there is one) or `passed`, and the context renders only on a change. **Cheer**: a lesson whose stage turns `passed` after the page first told otherwise gets one of three cheers (`tutor.cheer.*`, at random), shown as the empty conversation's title or as a tutor turn below the messages, client-side only, so it costs no message; it goes when the stage leaves `passed` or the student sends a message in that lesson's chat. The box grows with the text up to 160px, with the send button as an arrow inside it and an Enter hint below. "Show earlier messages" pages back with `?before=`, keeping the reading position. Delete asks through `window.confirm`, then shows a new conversation. The 5-hour session (CYB-16) shows in the panel from `UsageContext`'s `tutorMessage`, read again after every message: at 90% used a notice above the messages gives the refill time, and its X keeps it closed for that window (`cyberstars.tutorNotice` in `localStorage` holds the window's refill time); at the limit a line above the box says when the student can chat again and the box is disabled, and a timer reads the usage again when the window ends, so it opens without a reload. A 429 whose message starts with `USAGE_LIMIT_ERROR` is a spent session (`tutor.errorLimit`, no Try again while it lasts); any other 429 is the per-minute limit
- **Landing page** (`apps/ui/src/pages/LandingPage.tsx` + `components/landing/`): what a visitor gets on `/`. `HomePage` renders it when nobody is signed in, and a student keeps the dashboard there. Top to bottom: its own `LandingNav` (the logo, the language switch and Sign in, no page links), the hero with `HeroPreview`, `ProofStrip`, `HowItWorks`, `FeaturesSection`, `FreeSection`, `Faq` and `CtaBand`, then `LandingFooter`. The footer's links scroll to the page's own sections (`#how`, `#features`, `#faq`) by hand, so the scroll is smooth unless reduced motion is on and the address stays the page's own. Every claim must hold for a visitor today: `ProofStrip` counts courses, lessons and challenges from the curriculum (`curriculumCounts`, leaving out a course badged "Coming Soon"), and the copy says where something needs an account (ten editor runs without one, progress, the forum). The pictures are the app's own pieces, not screenshots: `CodeStill` draws code in the editor's oneDark colours so CodeMirror stays off the landing page, next to the app's own `Field`, `caseLabel` and `ActivityHeatmap`. The hero shows an example from a lesson's text (`python/lists-for`), never a mission's solution, since solutions are only for signed-in students. `FeaturesSection` is five titled cards with no links (courses, algorithm challenges, the Linux terminal, the forum, and the AI tutor across the whole row; the forum and the tutor say they need a free account), drawn the same way in `FeaturePictures` (the tutor's is a conversation where each answer points at the idea and leaves the fix to the student, drawn with the panel's `TutorMark` and bubbles, its second turn only from 768px) (the courses bar chart counts lessons through `curriculumCounts`). `HowItWorks` pins the picture in a middle column on a wide screen while the steps scroll past on both sides, and stacks words and picture below 1024px. Only the landing page carries colour: `.landing-wash`, `.landing-wash-strong`, `.landing-glow` and `.landing-gradient-text` in `index.css`; the app stays flat. Every block fades in through `Reveal`: a 16px rise, once, on one curve and duration, with an optional `delay`. A block renders visible and only hides in a layout effect once its IntersectionObserver is in place, so content never stays stuck at transparent; it plays on its first visible pixel, never hides under reduced motion, and leaves alone a block already on screen in a pre-rendered page. Don't reuse the welcome tour's `.reveal` class: `WelcomePage.css` is global once loaded
- **Pre-rendered pages** (`apps/ui/src/seo/` + `apps/ui/scripts/prerender.tsx`, run after `vite build`): every public page is written as HTML, in English and under `/ro`, about 800 in all: the landing page, the course list and each course, every lesson and algorithm challenge (only `<slug>.md`, never a solution), the challenge lists, the Almanac and each article. `seo/pages.ts` decides the list (`buildPages`, from a `ContentSource` the script fills from disk): a title from the `seo.*` templates in the locales, the lesson's first lines as description (`summary`), the alternates for `hreflang` (a lesson, challenge or article without a translation gets no `/ro` page), a `lastmod` from the file's mtime, and JSON-LD (a `Course` on each course, an `ItemList` of courses, a `BreadcrumbList` on lessons, challenges and articles). Kotlin, "Coming Soon", is written with `noindex` and left out of the sitemap. `seo/head.ts` rewrites the shell's title, description, canonical and Open Graph tags per page, adds the `hreflang` links, robots and JSON-LD, and fails the build if the shell lost a tag; it also writes `dist/sitemap.xml` (there's no static one). Pages go to `dist/<address>.html` (`dist/index.html` for `/`, `dist/ro.html` for `/ro`). The landing page is the app's own `LandingPage` with the real curriculum, inside `<div data-prerender>`; every other page is plain HTML with real links from `seo/StaticPages.tsx` (lesson text through `react-markdown`, code as plain blocks, since `MarkdownRenderer`'s editors need a browser). The app draws over the HTML with `createRoot`. `public/boot.js`, loaded in the head before the first paint, sends an old `/#/...` link to its real address and a visitor who picked Romanian (`cyberstars.lang.v2` is `ro`) from an English address to its `/ro` twin, and hides the pre-rendered HTML everywhere but the landing page, and there too for a browser that last saw a signed-in student (`AuthContext` keeps `cyberstars.student` in `localStorage`, `wasSignedIn()`); while sign-in is still being checked `HomePage` shows such a browser the spinner and anyone else the landing page straight away. `public/` keeps `robots.txt` and `og-image.png`
- **Guests** (`apps/ui/src/components/layout/GuestGate.tsx`): a guest sees only Courses, Algorithms and Almanac in the sidebar, with Sign in at the foot (no Dashboard, no Community group). `GuestGate` wraps the routes and lets a guest open only the welcome page, `/getstarted`, `/courses(/:course)`, `/algorithms(/:lang)`, `/lesson/:category/:lesson` and `/almanac(/:slug)`; any other path, a new one included, goes to `/getstarted` with `state.from`, and `AuthPage` returns there after login (sign-up still goes to the tour). While sign-in is still loading it renders nothing on a gated path. The forum's reads require an account on the server too (`authenticateToken` on its GETs)
- **First-lesson tour** (`apps/ui/src/components/tour/`): a new account is held on `TOUR_LESSON` (`python/print`, in `packages/shared/constants.ts`) until it passes that lesson's tests. `TourGate` wraps the routes and sends every other path to `TOUR_PATH` while `user.onboardedAt` is null; sign-up navigates straight there. On the lesson, `LessonTour` opens on a language choice (kept in `LessonPage` state, since a language switch reloads the lesson and remounts the tour), then dims the screen with an SVG even-odd mask whose holes are the only clickable spots; a click on the dim part raises `TourNotice` bottom right. It walks the lesson in reading order: each stretch of text between code cells, every code cell (each has to be run: `CodeCell` dispatches a bubbling `CELL_RUN_EVENT` when a run ends), the mission (the lesson's last `h2` onward), the editor, a run of the student's code, then Run Tests. It finds its targets through `data-tour` attributes on `LessonPage`, which leaves out the editor's ⋯ menu while the tour runs. The server stamps `users.onboarded_at` in `progressService.markComplete` when the tour lesson is completed, so ending the tour is as judge-authoritative as completion. The migration backfilled existing accounts with `created_at`, so only new sign-ups see the tour. The redirect is client-side UX only; the API does not gate on it. E2E `signupViaAPI` marks its accounts onboarded, and `e2e/tests/code-tour.spec.ts` walks the tour with real runs
- **Judge results** (`apps/ui/src/components/judge/`): after Run Tests the lesson panel switches to a Result tab (on a phone the top switcher becomes Lesson | Result | Submissions | Code). `ResultPanel` shows the verdict and X / Y (`Verdict`), the test the run stopped on (`FailedCase`: input, the student's output, and the expected output only on a visible test; there the difference is marked, like a GitHub diff, when the lesson compares outputs as text, see below), the passed tests folded under a "Passed tests (N)" toggle (`PassedCases`: each test opens on its input, expected and actual output), and, on algorithm lessons only, the runtime against the reference (`Runtime`: totals and a per-test chart). `LessonPage` passes `showRuntime` for `ALGO_COURSE_KEYS` only: a course lesson just has to work, so it shows no timings, and the Submissions tab (`SubmissionsPanel`) leaves out its runtime column the same way. Linux lessons keep their own `TerminalTestResults`. The diff (`outputDiff.ts`, jsdiff) leaves matching lines plain, marks a missing or extra line whole and a changed line character by character: green backgrounds on what the expected output has and the student's lacks (`--diff-missing`), red on what the student's has wrong or extra (`--diff-wrong`). It needs the lesson's `comparator`, which `RunTestsResponse` carries and `SubmissionDetail` reads from the lesson when the attempt is opened: a `masked` or `unordered` lesson gets no diff, since a difference there didn't fail the test. Past 50,000 characters or 100 ms the outputs show as plain text
- **One look, no decoration**: the UI is flat and quiet: opaque surfaces, neutral hairline borders, a three-step text hierarchy, Inter for UI. There is no starfield, no animated backgrounds and no decorative emoji; icons come from `lucide-react`. The logo is `BrandMark` (`apps/ui/src/components/ui/BrandMark.tsx`), the accent star from `public/favicon.svg`

### Server (`apps/api/`)

- Express 5 + TypeScript, runs with tsx. The `@cyberstars/api` workspace: code in `apps/api/src`, with the Prisma schema, the integration tests and the judge scripts next to it, its own `package.json`. The root's `npm start`, `dev:server`, `db:*`, `check:tests` and `validate:tests` run its own scripts
- Nothing in the API reads the working directory: files that ship with the code are found from their own folder (`import.meta.dirname`), and the `.env`, `uploads/` and `media/radio/` stay at the repo root on the server's disk, named once in `apps/api/src/config/paths.ts`. Prisma doesn't load `.env` once a `prisma.config.ts` exists, so the Prisma config and the seed load it from there themselves
- `app.ts` exports the Express app (used by supertest); `server.ts` imports it and calls `listen()`
- Pages (`middleware/pages.ts`, `servePages`): every extensionless path outside `/api` and `/auth` gets its pre-rendered `dist/<address>.html` when there is one; an app-only page (`APP_ONLY_PATHS` in `packages/shared/routes.ts`, after stripping `/ro`) gets the app shell with `X-Robots-Tag: noindex`; anything else gets the shell with a 404 and `noindex`. It runs before `express.static`, which would otherwise redirect `/courses` to `/courses/`
- Three-layer architecture: Routes → Controllers → Services → Repositories
- Zod schemas in `apps/api/src/schemas/` validate all request bodies via `validateBody()` middleware
- Auth: JWT in httpOnly cookies, bcryptjs password hashing. The JWT payload carries only `{ id }`. The role is **never** in the token; any role/authorization check reads it fresh from the DB by the authenticated user id (`userRepo.getRole`), so a tampered client/cookie cannot escalate
- Admin: `requireAdmin` middleware (in `middleware/auth.ts`, runs after `authenticateToken`, DB-authoritative role check) gates `/api/admin/*`. `GET /api/admin/stats` returns platform aggregates (users/progress/forum/support) cached ~5min in `admin.service.ts` to spare the VPS, plus **live** in-memory code-execution metrics (`code-container.service.liveMetrics`) read on every call; `?fresh=1` force-bypasses the cache (used by the dashboard's Refresh button). Code-exec stats are live-only: editor runs are never persisted, and the stored judge attempts (submission history, below) feed no admin metric
- **Visitor counts** (`visits.service.ts` + `visits.repository.ts`, CYB-65): the app's `usePageViews` (mounted at the root) posts each page it shows to `POST /api/visits` (`optionalAuth`, 300/min/IP, always 204, a storage error is only logged): the full path with `/ro`, and on the first page only the referrer's domain (`""` for none; left out when the referrer is our own site, like the reload after a language switch). The server drops anything whose user agent says bot, crawler or script, and every page an admin or founder opens (one `getRole` per signed-in view), then keys the visitor by a SHA-256 of the day's salt, the IP and the user agent; no IP and no `guestId` is stored, so a visitor can't be followed from one day to the next. A day is Romania's (`Europe/Bucharest`). The salt lives in `visit_salts` for its day only, so a deploy doesn't count everyone twice. `scheduleRollUp` (from `server.ts`, at start and hourly) turns every finished day's `page_visits` into `visit_totals` rows (dimension `all`/`page`/`source`/`auth`/`lang`) and deletes its visits and salt in one transaction. A Romanian page counts as its English twin under `page`, told apart by `lang`. Sources are `google`, `bing`, `reddit`, `hackernews`, `devto`, `github`, `direct` or the referring domain. `GET /api/admin/visits?range=30|90` adds up the totals plus the not-yet-rolled-up days live, with new accounts a day; over several days a visitor counts once per day. The admin page shows it in `components/admin/VisitorsSection.tsx`, with `DailyChart` drawing each line as SVG (no chart library). **Guest visits** (CYB-66): a guest's page view also makes their `guest_visits` row for the day (one `INSERT ... ON CONFLICT (day, visitor)`, source and lang from the first page) and adds the page as a `visit_steps` row. `useGuestSteps` (mounted next to `usePageViews`, guests only) queues a `click` step for any element with `data-track="<name>"` (a fixed kebab name in the code, never its text; the zod schema refuses anything else) and a `scroll` step when the window gets past 25/50/75/100% of a page that scrolls; the queue rides with the next page report so steps land before the page they led to, or goes to `POST /api/visits/steps` after 10s, at 30 steps, or on `visibilitychange`/`pagehide` (`keepalive`). Steps join today's visit for the same hash only; a signed-in report adds no page step, only what was queued before sign-up. A visit stops at 500 steps. Steps are ordered by id and carry no time; the visit keeps only when its first page came in (`started_at`, empty on visits from before it was kept), which the admin list shows as HH:MM in Romania's time. Java injection splices the initializer of a variable declaration (field or method-body local), so OOP lessons bind values into named locals before `new X(...)` rather than passing literals directly to constructors; the mission names those variables. Injection keeps away from a helper's own names: Python skips an assignment to a parameter of its enclosing function and, once the variable is assigned outside every function and class, uses only those; Java uses only `main`'s own statements once the name has one there (so a field `int customers = 0;` keeps its value). Structure rules per lesson: `requires`/`forbids` with kinds `call`, `variable`, `function` (without a `name`: any function of the student's own, main and constructors aside), `loop` (optional `type`: `for` (Java for-each included), `while`, `do_while`, or Python-only `comprehension`; untyped = any loop), `recursion` (a function that calls itself: by name, or a method through `self.`/`this.`), the statements `if`/`switch` (Python's `match`)/`break`/`continue`/`try` and `nested_loop`, `operator` (by spelling: `&&`, `and`, `%`, `<<`; a compound assignment counts as its operator), `class` (the student's own, optionally by `name`; in Java the class holding main doesn't count) and `object` (an instance of one), Java-only `extends`/`implements`/`interface`/`enum`/`override` (`@Override`, or redeclaring a method of an own parent class)/`overload`/`modifier` (`static`, `final`, `private`, `abstract`...; static or private on a helper or field next to main doesn't count)/`instanceof`/`cast`, Python-only `return` (a function returns a value)/`default_param`/`slice`, C-only `struct`/`typedef`/`pointer` (one the student declares: not main's `argv`, a cast or a sizeof)/`deref` (`*p`, `p->x`; `p[i]` doesn't count)/`sizeof`/`define`/`enum`, `fstring`, `int_literal`, `comment` (require-only; `contains` substring matched whitespace-insensitively against real comments: py `tokenize`, java lexical scan, c tree-sitter `comment` nodes), and `string_expr` (forbid-only; catches the "wrap the line in quotes" fake-comment cheat; py/c only, N/A in Java where an unknown kind fires as a forbid). Comment lessons pair `comment contains <expr>` with `forbids string_expr` so quoting-out or deleting the target line fails. A Python rule with `in: <function>` looks only inside that function and the helpers it calls (string-reverse bans `[::-1]` in `reverse_text` while its word-order step slices). A runner takes a kind it doesn't implement as present, so `validate:tests` rejects a kind (or loop type, or `in`) the lesson's language lacks. Each lesson requires the constructs it teaches or its mission explicitly asks for, and its variants include a reject that gets the right output without each of them **Locale pairing invariant**: `ro/<slug>-tests.json` + `ro/<slug>-solution.md` are a unit (RO lessons use Romanian identifiers); if a lesson has a RO solution it MUST get a RO tests file, or injection silently no-ops and hardcoding passes. `hasTests` is generated into `curriculum.json` from the EN tests-file existence. UI: tested lessons show a Run Tests button; untested main-course lessons show the button disabled with a "Coming soon"/"Urmează" tooltip. There is **no manual "mark complete"**; completion comes only from passing the judge, and is **server-authoritative**: `tests.controller.runTests` calls `progressService.markComplete` itself on a `passed` verdict for a logged-in user (guests have no progress), so completion cannot be spoofed by a direct API call. The client just refreshes progress afterward. Endpoint `POST /api/tests/:courseKey/:lessonSlug/run` (10 runs/min/owner, works for guests)
- **Judge run flow** (`runLessonTests`): the runner streams a header line, then one JSON line per case, and waits for the server's `next`/`stop` reply on stdin (`dockerConverse` in `docker-exec.ts`, ~0.1 ms per round trip; re-entering the container in chunks would cost a new `docker exec` + runner start each time, ~0.2 s for Python/C and ~1.1 s for Java), so a run **stops at the first failing case**: `cases` holds the passed cases plus at most one failed case, last, with `index` pointing into the spec; a passed case carries its normalized `expected` and `actual` output (hidden ones too, since the student's program already produced it), while a failed case carries `actual` and, only when it is visible, `expected`; `passedCount`/`total` are the X / Y. Structure failures fail the run but every case still runs; a syntax error gives `cases: []`. Each runner times every program run (wall clock, compile excluded) and the server reports `userMs`/`solutionMs` per case in ms rounded to one decimal, plus `runtimeMs`/`referenceMs` summed over the cases timed on both sides. Bulk `"generated": true` cases (always hidden, appended after the hand-written ones; `validate:tests` caps a lesson at 50 cases for Python/C, 20 for Java) get their reference output cached in server memory (`reference-cache.ts`: LRU, 4096 entries / 4M chars, keyed by course, locale, slug, solution source, case and comparator; never for `masked`/`unordered` lessons, never from a failed reference run). On a hit the case goes to the runner with `skipSolution` (for C, `prepareC` leaves its `solutionSrc` out) and carries no `solutionMs`; hand-written cases always run the reference fresh. Time: each program is cut at 5 s and a timeout ends the run; the cases share a per-language budget (`budgetMs`: Python/C 30 s, Java 45 s, counted from the runner's header), and once a case finishes past it the next case is reported as `error: 'timeout'`. The exec's hard ceiling is `baseTimeoutMs + budgetMs + caseBudgetMs` whatever the case count (56/58/91 s for Python/C/Java); past it the container is dropped. `npm run check:tests <course>[/<slug>][:en|:ro]` grades each lesson's own solution through the real judge and prints the run time; it also grades the lesson's variants in `packages/content/variants/<course>/<slug>/`, where every `accept-*` (another correct solution: other names, another approach) must pass and every `reject-*` (a cheat or a near miss: hardcoded output, the wrong loop, an off-by-one) must fail
- **Translations**: English is the source of truth and lives at the top level. Optional Romanian translations sit in a `ro/` subfolder beside the English source (`packages/content/lessons/<course>/ro/<slug>.md`, reusing the same slug); `lessonService.getLocalizedText` requests the `ro/` path and falls back to English when it's missing, so a course can be translated one lesson at a time and English-only lessons work in both languages. The almanac follows the same pattern under `public/almanac/ro/` (`almanacService`). Linux `-setup.json` sandbox files can be localized too: an optional `packages/content/lessons/linux/ro/<slug>-setup.json` (translated filenames + content) is picked up when the client's active language is `ro`: `useTerminalSession` passes `lang` on session create, `terminal-session.service.loadSetup` falls back to the English copy when no RO variant exists, and switching language mid-lesson tears down and recreates the sandbox. Romanian lesson **code and output must stay ASCII**: no diacritics inside ` ```py `/` ```text ` fences or `-code.md` files (printed strings, expected output, comments); diacritics belong only in the RO prose/theory

### Algorithm challenges (`packages/content/algorithms/{python,java,c}/`)

- Separate from main lessons, mapped via `courseDir` in `packages/content/paths.ts`: course keys `algo-python`, `algo-java`, `algo-c` resolve to `packages/content/algorithms/{python,java,c}/`
- Each challenge has 3 files: `<slug>.md` (problem statement with Input/Output/Examples), `<slug>-code.md` (starter code), and `<slug>-solution.md` (single fenced runnable block, powers the same "Show Solution" button/`SolutionModal` as lesson solutions)
- 20 challenges each for Python and Java; C has 32 (20 core + 12 concurrency-focused: fork/pipe/threads/mutex/semaphore), Easy/Medium/Hard, registered in `apps/api/prisma/seed.ts`
- Starter code (`<slug>-code.md`) is empty: Python is 0 bytes, Java/C are 3 blank lines (no compilable wrapper); students write the full solution, including the `class Main`/`#include`+`int main()` boilerplate for Java/C, from scratch
- Solutions are provided for all 72 challenges (Python 20, Java 20, C 32), EN + RO
- Algorithm challenges are **judge-graded** (the same server-authoritative judge as main-course lessons; see Lesson content): all 20 algo-python + all 20 algo-java + all 32 algo-c challenges ship a `<slug>-tests.json`. The 12 algo-c concurrency challenges (fork/pipe/threads/sem) are now graded too via the nondeterminism-tolerant comparators below. Algo challenges read stdin, so tests use the oracle + per-case `stdin` model (no injection); a single EN tests file suffices unless the RO solution's output diverges (translated words, or Romanian command keywords in stdin), which gets a paired `ro/<slug>-tests.json`. matrix-multiply (java) / matrix-transpose (c) have fixed input, so they use a `structure.requires: loop` check. Because algo is now completable, XP display is **enabled** on algo pages (LessonPage header + completion toast). `hasTests` distinguishes graded from ungraded challenges (Run Tests button state)
- **Generated hidden cases**: 67 of the 72 challenges append bulk `"generated": true` cases after the hand-written ones (C about 30, Python 25 to 30, Java up to the 20-case cap), mirrored into `ro/<slug>-tests.json` where one exists (translated only when the stdin itself is Romanian). They cover the input's shape rather than random values: every stated bound, a single element, all values equal, sorted and reverse-sorted input, duplicates, negatives, the longest allowed input. None for fork-chain, fork-two-pids and fork-workers (`masked`/`unordered`, which `validate:tests` forbids) or matrix-transpose/matrix-multiply (no input). Main-course lessons are graded LeetCode-style: an exact name is required only for an inject key or a function/class the mission names as the thing to write (everything else is the student's choice), the construct the lesson teaches is required (a typed loop, a function, recursion, the taught call), and every lesson with input carries hidden cases up to the cap, kept inside the domain its mission states (a case whose answer the mission doesn't settle, such as a tie, is left out)
- **Stated input limits**: every challenge that reads input states its limits in the `### Input` list of `<slug>.md` and `ro/<slug>.md`: sizes, value ranges, string lengths, character sets, and separators such as "one or more spaces". They are written as `<=` with powers (`1 <= N <= 200`, `-10^9 <= x <= 10^9`, `2^31 - 1`, `2·10^9`; Prettier turns a `*` into emphasis). Every case, hand-written or generated, must respect them, and the bounds must keep the reference solution correct (e.g. `rectangle-calc` keeps the area within an `int`, `iterator-pattern` keeps `end` well below `Integer.MAX_VALUE`). A case that needs more than the statement allows means changing the statement, in both languages
- **Output comparators** (`compareOutputs` in `lesson-tests.service.ts`, `TestComparator` in `packages/shared/tests.ts`): `trimmed` (default; trims trailing whitespace + trailing blank lines), `exact` (byte equality), `masked` (collapses every `\d+` run to `#`, for fork/getpid lessons that print nondeterministic **PIDs** in a fixed line order), `unordered` (compares the **multiset of lines**, for thread/process lessons whose line **order** varies between runs, e.g. fork-workers, os-threads, os-semaphores), `template` (the output must match the spec's `template`, where each `<word>` is a blank any text with a visible character fills on its line; the template, not our solution's output, is what the student is shown as expected, and `validate:tests` wants the comparator and the template together. `python/print`, the tour lesson, uses it so the student prints their own name and age). `masked`/`unordered` lessons pair a minimal `structure.requires` on the libc primitive (`fork`/`pthread_create`/`sem_wait`/`pipe`): libc names the student can't rename, so freestyle on identifiers stays intact while hardcoding the fixed output is blocked. Fixed-input deterministic lessons (os-pipes, os-semaphores-signal, recap-os) rely on the same structural gate since varied stdin can't protect them

## Key conventions

- Vite proxies `/api`, `/auth`, and `/ws` to the Express server (configured in `apps/ui/vite.config.ts`)
- Course metadata is centralised in `apps/ui/src/constants/courses.ts` via `courseMeta(key)` and `courseTitle(key)`, the single source of truth for icons, colors, labels
- Course key constants live in `packages/shared/constants.ts`: `MAIN_COURSE_KEYS`, `ALGO_COURSE_KEYS`, `TERMINAL_COURSE_KEYS`, `ALL_COURSE_KEYS`
- Gamification is derived client-side from `UserLessonProgress` counts; no separate gamification tables. **Badges**: "First Steps" (1 lesson) and Bronze/Silver/Gold tiers (10/20/30 lessons per course); new earnings trigger a 5s toast. **XP & levels**: XP is a _derived_ quantity, never stored nor accepted from a client. The server recomputes `earnedXp`/`totalXp` in `getCourseProgress` from the sortOrder of judge-completed lessons (`xpForLesson(sortOrder) = 10 + (sortOrder - 1)`; sortOrder is **1-based** per `packages/content/curriculum.ts`, so the first lesson is worth 10 XP), so a tampered client can only fool its own display (completion rows are server-authoritative). Completion rows created by the old manual mark-complete flow are **grandfathered**: they stay in the DB and still yield XP (deliberate decision: no destructive migration; anti-cheat is forward-looking only). Quadratic level curve `levelFromXp(xp) = floor(sqrt(xp/100)) + 1` with cosmos-themed titles (`level.title.1..10` i18n keys); `useGamification` aggregates XP across courses. Shown in Profile (level banner + progress bar), Topbar (level chip), and the lesson-completion toast (`+N XP`). An XP-ranked leaderboard (`/api/leaderboard`) sits behind the `leaderboard` preview gate (admins only on prod), and the route also adds `authenticateToken` so guests are kept out (the page exposes `total`, the platform-wide account count)
- **Daily picks** (`/api/daily`, auth-required; `daily.service.ts` + `daily.repository.ts`): `GET /api/daily` returns today's `lesson` and `algo` picks plus `bonusRatio`. Each pick is chosen **deterministically per day+kind** from a course pool (`lesson` = main + terminal courses, `algo` = algo courses) via a stable hash seed, so every user sees the **same** pick that day; the concrete row is then persisted **per user** (`DailyPick`, unique `[userId, date, kind]`) only so the bonus can be tracked. Only judge-completable lessons are eligible (an ungraded pick would be unclaimable). Completing today's pick **on its day** grants a one-time bonus of `DAILY_BONUS_RATIO` (0.2 = **+20%**) of the lesson's base XP: `progressService.markComplete` calls `dailyService.awardBonusForCompletion` (idempotent, sets `bonusAwarded`), and `getCourseProgress` folds awarded bonuses back into `earnedXp` via `dailyRepo.getAwardedSlugs`. Surfaced on the home page and the `/laniakea` explorer (`LaniakeaExplorerPage`)
- Profile features (avatar upload, bio, status with 24h expiry) via `/api/profile` routes with multer + magic-byte validation. Uploads served from `/uploads` static dir. Profile editing plus the language/privacy toggles live on a dedicated `/settings` page (moved out of the Topbar dropdown). Five per-user privacy flags on `User` (`showBio`/`showStats`/`showProgress`/`showActivity`/`showConnections`, default on) are set through the same `PATCH /api/profile` and gate the public profile's sections
- Public profiles at `/u/:userId` (reached from the leaderboard rows) via `GET /api/users/:id/profile` → `public-profile.service.ts`, gated with the same `leaderboard` feature key and logged-in only (the route uses `authenticateToken`, so guests get 401; no guest can view a profile or the forum username links that share this gate). Name/avatar/member-since are always public to any logged-in viewer; bio/status, stats (lessons done, active courses, streak), progress (level, XP, rank, badges), the activity heatmap, and the connections list (truncated for display but with the true total `count`) each appear only when the target's matching privacy flag is on; the owner viewing their own profile (`isSelf`) always sees everything. The payload also carries `connectionRelation` (`self`/`none`/`pending_outgoing`/`pending_incoming`/`connected`) for the profile's connect button. Streak logic is shared via `activity.service.computeStreak` (used by both this and `GET /api/profile/activity`)
- Dark theme uses CSS custom properties with accent purple `#6C5CE7`, Inter for UI, JetBrains Mono for code. **The fonts ship with the app** (`@fontsource-variable/inter` and `@fontsource-variable/jetbrains-mono`, imported at the top of `index.css`), never from a font host, so the CSP's `font-src` is `'self'` only. Text reaches them through `--font` / `font-sans`, code through `--mono` / `font-mono` (Tailwind's own variables point at ours through `@theme inline`); never name a family in a component. CodeMirror sets plain `monospace` itself, so `CodeEditor`'s `appFont` theme puts it back on `--mono`. Element defaults (`input`, `button`, `pre`...) live in `@layer base`, below the utilities: an unlayered element rule would beat every Tailwind class. `e2e/tests/fonts.spec.ts` and `code-fonts.spec.ts` check it in the browser
- Lesson completion is driven **only** by passing the judge and is **server-authoritative**: `tests.controller.runTests` calls `progressService.markComplete` when the judge returns `passed` for a logged-in user. There is no client-writable completion endpoint (`POST/DELETE /api/progress/:courseKey/:lessonSlug/complete` were removed), so completion cannot be spoofed. The client reflects it optimistically then `refresh()`es. There is no manual "mark complete" button anywhere. Python, Java, and C main-course lessons (including the C OS block 39–47), all 55 Linux/terminal lessons (via the terminal judge), plus the graded algorithm challenges (all algo-python/algo-java, all 32 algo-c including the 12 concurrency ones) are judge-completable; only Kotlin (course "Coming Soon") lacks tests and is not completable yet
- The user communicates in Romanian; code and docs stay in English
- **No ALL-CAPS anywhere** unless the user explicitly asks for it. This covers UI copy, i18n strings, lesson content/output, comments, and CSS uppercase transforms (`uppercase`, `text-transform`). Prefer normal sentence case for new labels and section headers
- i18n: bilingual UI (English default + Romanian) via i18next. The address decides the language (`langFromPath`: `/ro` and below is Romanian); a language switch goes through `switchLanguage`, which redraws at once and moves the browser to the twin address (`twinPath`), a full reload since the router's basename changes. The lesson tour keeps its language pick across that reload in `sessionStorage`. A change is also saved to `localStorage` (`cyberstars.lang.v2`), which only `public/boot.js` reads, to send someone who picked Romanian to `/ro`. UI strings in `apps/ui/src/i18n/locales/{en,ro}.json` (keep keys in sync). Lesson/almanac content is translated by file in `/ro` subfolders with English fallback (see Lesson content). `SUPPORTED_LANGS = ['en', 'ro']` in `apps/ui/src/i18n/index.ts`
- **The look lives in CSS custom properties** on `:root` in `index.css`. Reach for a token rather than a raw colour. The surface tokens are `--panel-bg` / `--panel-border` (content panels), `--glass` (a tint on top of a panel: inputs, message bubbles, output headers), `--popover` (floating surfaces), `--chrome` (the sticky topbar), `--page-bg`, and `--border`

- Inside the app shell a page lays itself out on the room it has, with container variants (`@xl:`, `@2xl:`, `@3xl:`...) against the shell's `@container` page wrapper, not on the window (`md:`, `lg:`), since the sidebar and the tutor's panel take part of it. Viewport variants stay for phone-only touches (`sm:` paddings) and for the bare routes
- All cards, panels, and containers use the **`.panel`** class in `index.css`, the canonical single-source surface (`--panel-bg` + `--panel-border` + `--radius`). Prefer adding `panel` over re-inlining a background/border
- Borders use `border-[var(--border)]`, a neutral hairline. Do **not** hardcode `border-[var(--accent)]/20|30|40` for resting borders; keep the accent only for `focus:`/`hover:`/`active:` states and for genuinely selected chips
